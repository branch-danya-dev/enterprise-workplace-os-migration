# Context and Scope

## Project Context

The project was part of a large-scale enterprise transition from
Microsoft Windows to Astra Linux within a banking environment.

The migration was driven by organizational requirements associated
with the transition to domestic software and increased information
security requirements.

At the organizational level, the target scope included workplace
migration for bank employees whose working environment was based on
Microsoft Windows.

A workplace was not treated as an operating system in isolation.
Each workplace depended on a combination of:

- user role and business activities;
- installed software;
- access to enterprise services;
- hardware configuration;
- connected peripherals;
- location and working mode;
- application compatibility with the target operating system.

Because of these dependencies, migration readiness differed
significantly between users and departments.

## Program Scope

The overall migration program targeted enterprise workplaces across
the bank.

Each user had at least one assigned workplace that was expected to be
transitioned from Windows to Astra Linux according to the migration
program.

Migration could not be performed simultaneously for all users because
workplaces had different software dependencies and business
criticality.

The rollout therefore required segmentation and phased migration.

## Operational Scope

My area of responsibility was the workplace environment and the
components directly associated with it.

This primarily included:

- user workplaces;
- operating system migration status;
- installed workplace software;
- software compatibility issues;
- migration readiness;
- coordination of workplace-related incidents and blockers.

Adjacent domains such as office equipment and systems owned by other
teams were outside my direct responsibility.

However, dependencies on those domains were taken into account when
they affected workplace migration.

## Key Migration Constraint

The primary migration constraint was software compatibility.

A significant number of business and productivity applications either:

- had no Linux-compatible version;
- had no functionally equivalent replacement;
- required adaptation;
- required vendor development;
- or could not be replaced within the migration timeline.

Examples included complex productivity tools, spreadsheet software,
diagramming applications, specialized business applications and
1C-based software.

Such dependencies could prevent a workplace from being included in a
migration wave until an acceptable solution was available.

## Migration Success

A workplace was considered successfully migrated when:

1. the user workplace had been transitioned from Windows to Astra Linux;
2. the required workplace environment was operational;
3. the user could continue the agreed business workflow using the
   supported software and services available for the target environment.

Operating-system installation alone was therefore not sufficient to
classify the workplace as operationally migrated.
