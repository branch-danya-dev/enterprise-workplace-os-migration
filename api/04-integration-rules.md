# Integration Rules

## Purpose

This document defines integration behavior for the Migration Management API.

The rules describe how external systems should interact with the API when
sending migration events, handling retries, avoiding duplicates and processing
temporary failures.

The goal is to keep migration data consistent even when network or system
failures occur.

---

# 1. Idempotency

## IR-001 — Migration Attempt Idempotency

Each migration attempt reported by an external migration tool must contain a
stable external identifier.

Example:

```json
{
  "externalAttemptId": "mig-20260408-106-001",
  "workplaceId": 106,
  "executionType": "automated",
  "result": "failed"
}

The combination of source system and externalAttemptId must uniquely
identify one migration attempt.

Repeated requests with the same identifier must not create duplicate migration
attempt records.

IR-002 — Duplicate Request Handling

If the API receives the same migration attempt more than once, the API should
return the result associated with the previously processed attempt instead of
creating another business event.

Example:

First request:

externalAttemptId = mig-20260408-106-001

Result:

Migration attempt 4001 created

Repeated request with the same identifier:

externalAttemptId = mig-20260408-106-001

Result:

Existing migration attempt 4001 returned

No second migration attempt is created.

IR-003 — Conflicting Duplicate

If the same externalAttemptId is received with different business data, the
request must be rejected.

Example:

Previously registered:

{
  "externalAttemptId": "mig-001",
  "result": "failed"
}

Later request:

{
  "externalAttemptId": "mig-001",
  "result": "successful"
}

The API should return:

409 Conflict

Example error code:

IDEMPOTENCY_CONFLICT

This prevents one external event identifier from representing two different
events.

2. Retries
IR-004 — Retry Temporary Failures

External integrations may retry requests when the failure is considered
temporary.

Examples of temporary failures:

connection timeout;
connection reset;
HTTP 502;
HTTP 503;
HTTP 504.

Retries should not be used for permanent validation or business errors.

IR-005 — Do Not Retry Business Errors Automatically

The following responses should normally not be retried without changing the
request:

400 Bad Request;
404 Not Found;
409 Conflict caused by invalid business state.

Example:

400 INVALID_MIGRATION_RESULT

Retrying the same request will not solve the problem.

The calling system should correct the request or escalate the issue.

IR-006 — Retry Backoff

Repeated retry attempts should use increasing delays.

Example strategy:

Attempt 1
↓
wait 2 seconds

Attempt 2
↓
wait 5 seconds

Attempt 3
↓
wait 15 seconds

Attempt 4
↓
stop automatic retries

Exact retry intervals are implementation-specific and may be defined by
infrastructure standards.

IR-007 — Maximum Retry Attempts

Integrations must not retry indefinitely.

After the configured retry limit is reached, the request should be placed into
an error or manual investigation flow.

The failure must remain traceable.

3. Timeouts
IR-008 — Client Timeout

External systems should use a finite timeout when calling the Migration
Management API.

A caller must not wait indefinitely for an API response.

Timeout values are implementation-specific and should be agreed between
integration participants.

IR-009 — Timeout Does Not Mean Request Failure

If the caller times out, it must not assume that the API failed to process the
request.

Example:

Migration Tool
    |
    | POST migration attempt
    v
Migration API
    |
    | record created successfully
    v
Database

Response is lost

From the Migration Tool perspective the result is unknown.

Therefore retrying the request must use the same idempotency identifier.

4. Migration Attempt Contract Extension

The migration attempt request should include:

Field	Type	Required	Description
externalAttemptId	string	yes	Stable attempt identifier generated by the source system
sourceSystem	string	yes	System reporting the migration result
workplaceId	integer	yes	Workplace identifier
executionType	string	yes	automated or manual
result	string	yes	successful or failed
migrationDate	datetime	yes	Attempt start time
completedAt	datetime	no	Attempt completion time
technicalError	string	no	Technical failure description

Example:

{
  "externalAttemptId": "mig-20260408-106-001",
  "sourceSystem": "automated-migration-tool",
  "workplaceId": 106,
  "executionType": "automated",
  "result": "failed",
  "migrationDate": "2026-04-08T09:00:00Z",
  "completedAt": "2026-04-08T09:42:00Z",
  "technicalError": "OS deployment failed"
}
5. State Transition Rules
IR-010 — Migration State Must Follow Allowed Transitions

External integrations must not arbitrarily set workplace migration status.

Status changes are controlled by the Migration Management Service.

Example valid transition:

scheduled
↓
migration_in_progress
↓
migrated

Example failure transition:

scheduled
↓
migration_in_progress
↓
manual_migration_required

Example manual recovery:

manual_migration_required
↓
migrated
IR-011 — Successful Automated Migration

When a successful automated migration attempt is registered, the service may
change the workplace status to:

migrated

provided no additional operational blocker requires a transitional state.

IR-012 — Failed Automated Migration

When an automated migration attempt is registered with:

result = failed

the workplace status must transition to:

manual_migration_required

if the failure requires Workplace Support intervention.

IR-013 — Successful Manual Migration

A successful manual migration attempt may move a workplace from:

manual_migration_required

to:

migrated
IR-014 — Invalid State Transition

A request that would produce an invalid state transition must be rejected.

Example:

Current status:

blocked

Request attempts to register migration completion without resolving the active
blocker.

Possible response:

409 Conflict

Example error:

{
  "code": "INVALID_MIGRATION_STATE_TRANSITION",
  "message": "Workplace cannot be marked as migrated while an active blocker exists",
  "details": {
    "currentStatus": "blocked",
    "requestedStatus": "migrated"
  }
}
6. Transaction Consistency
IR-015 — Attempt and Workplace Status Update

Recording a migration attempt and updating the workplace migration status
should be treated as one logical operation.

Example:

Create MigrationAttempt
+
Update Workplace status

The system should avoid a state where:

MigrationAttempt = failed

but:

Workplace = migrated

because one database operation succeeded and the other failed.

IR-016 — Postponement Consistency

Approving a postponement may require several related changes:

PostponementRequest = approved

Old schedule = postponed

New schedule = created

New migration date = assigned

These changes should remain logically consistent.

Partial updates should not leave the workplace with conflicting active
migration dates.

7. Concurrency
IR-017 — Concurrent Modification

The service should detect conflicting updates where multiple clients attempt
to modify the same migration object at the same time.

Example:

Support Team A:

approve postponement

Support Team B:

reject postponement

Both operations must not succeed.

The second conflicting request should be rejected.

Possible response:

409 Conflict
IR-018 — Already Resolved Objects

Resolved business objects should not normally return to an unresolved state
without an explicit supported business operation.

Examples:

PostponementRequest:
approved -> pending

should be rejected.

MigrationBlocker:
resolved -> open

should require an explicit reopen operation if the business process supports
it.

8. Event Ordering
IR-019 — Out-of-Order Events

The service should not assume that integration events always arrive in the
same order in which they occurred.

Example:

Actual order:

09:00 migration started
09:40 migration failed

Network delivery:

09:40 failure event received first
09:00 start event received later

Where event ordering matters, event timestamps or sequence identifiers should
be used to validate the current state.

IR-020 — Stale Event Protection

An older event must not overwrite a newer confirmed migration state.

Example:

Current state:

migrated

A delayed event arrives:

migration_in_progress

The service should reject or ignore the stale event rather than moving the
workplace backwards incorrectly.

9. Error Handling

Integration errors use the common API error contract.

Example:

{
  "code": "IDEMPOTENCY_CONFLICT",
  "message": "The external attempt identifier has already been used with different data",
  "details": {
    "externalAttemptId": "mig-20260408-106-001"
  }
}

Recommended integration-related error codes:

IDEMPOTENCY_CONFLICT
INVALID_MIGRATION_STATE_TRANSITION
ACTIVE_SCHEDULE_ALREADY_EXISTS
ACTIVE_POSTPONEMENT_REQUEST_EXISTS
POSTPONEMENT_ALREADY_RESOLVED
BLOCKER_ALREADY_RESOLVED
STALE_EVENT
VALIDATION_ERROR
10. Logging and Traceability
IR-021 — Correlation Identifier

Requests between integrated systems should contain a correlation identifier
where supported.

Example HTTP header:

X-Correlation-ID: 68dbea3d-4512-4a41-bd57-b50a752a4f37

The same identifier should be included in relevant logs across participating
systems.

This allows support teams to trace one operation across multiple services.

IR-022 — Integration Logging

Integration logs should contain enough information to identify:

timestamp;
source system;
endpoint;
correlation identifier;
external event identifier;
workplace identifier;
processing result;
error code where applicable.

Sensitive data should not be logged unless required and explicitly permitted.

11. Security
IR-023 — Authentication

External systems must authenticate before accessing protected API operations.

The exact authentication mechanism is outside the scope of this portfolio
model.

Possible enterprise mechanisms include:

OAuth 2.0;
service credentials;
mutual TLS;
corporate API gateway authentication.
IR-024 — Authorization

Authentication alone does not grant access to every API operation.

Permissions should depend on the calling system or user role.

Example:

Automated Migration Tool:

can create migration attempts
cannot approve postponement requests

Workplace Support:

can read migration failures
can register manual migration attempts

Service Desk integration:

can create postponement requests
cannot directly mark workplaces as migrated
12. Integration Principles

The integration design follows these principles:

External systems report facts; the Migration Management Service controls
migration state.
Business events must have stable identifiers where duplicate delivery is
possible.
Temporary technical failures may be retried.
Permanent validation and business errors should not be blindly retried.
A timeout means the result is unknown, not necessarily failed.
Duplicate delivery must not create duplicate business effects.
Invalid or stale state transitions must be rejected.
Related state changes should remain transactionally consistent.
Integration operations must remain traceable across systems.
Security permissions must reflect the responsibility of each integrated
system.
